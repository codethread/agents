# Pi 0.99.1 session schema

Verified against the then-installed `@earendil-works/pi-coding-agent` 0.99.1
`docs/session-format.md`, `docs/message-types.md`, `docs/compaction.md`,
`dist/core/session-manager.d.ts`, and `dist/core/messages.d.ts`, plus
`@earendil-works/pi-ai` 0.99.1 `dist/types.d.ts` on 2026-10-01. Field usage was
checked against 315 local session files timestamped 2026-09-27 to 2026-10-01
(local sessions use file format 3; `CURRENT_SESSION_VERSION` is 3). File-format
version 3 does not identify the Pi release, and 0.99.1 was only the release
installed when this reference was verified; the corpus is timestamp-selected,
not writer-identified (see
[1.0.0 verification](#100-verification-2026-10-02) for the currently installed
release). The previous snapshot is [0.87.1](0.87.1.md).

## 1.0.0 verification (2026-10-02)

Pi `1.0.0` is the installed release and this reference still applies. A
read-only comparison against the 0.99.1 package found byte-identical session
schema artifacts: `docs/session-format.md`, `docs/message-types.md`,
`docs/compaction.md`, `docs/sessions.md`,
`dist/core/session-manager.{js,d.ts}`, `dist/core/messages.{js,d.ts}`,
`dist/core/compaction/`, and `@earendil-works/pi-ai/dist/types.d.ts` (sha1). The
1.0.0 runtime bundle still uses `CURRENT_SESSION_VERSION = 3` with the same
entry construction. A representative session inspected while 1.0.0 was
installed
(`2026-10-02T09-57-48-945Z_01a0fc0c-7111-7388-b09a-0e63798e91f9`, millstrand-ui)
and 67 other sessions timestamped after the 1.0.0 install exposed only the entry
types, roles, and fields documented here; the optional `endTurn`, `deferred`,
`responseModel`, and `providerThinkingLevel` fields were not observed.

Scope: installed 1.0.0 docs, types, source, the bundle's schema constants, and
local session records, inspected read-only on 2026-10-02; no resume, migration,
or write path was exercised. Sessions are selected by timestamp, not proven
writer metadata: the session header's `version: 3` is the file-format version,
and neither the 2026-09-27..2026-10-01 corpus nor the newer sessions record the
release that wrote them. An installed release at inspection time is not writer
evidence for either 0.99.1 or 1.0.0.

## Changes since 0.87.1

No new session entry types; every 0.87.1 entry type and field is still valid.
The differences are message-level, mostly from codemode/MCP tool orchestration:

- Assistant messages gained `thinkingLevel`, `rawStopReason`, `responseModel`,
  `responseId`, `providerThinkingLevel`, `diagnostics`, `errorMessage`,
  `endTurn`, and `deferred` (`DeferredHandle`) with a `"deferred"` stop reason.
- Tool results gained optional `usage` (nested model work) and `nestedCalls`
  (`NestedToolCalls`), populated by tools that call `ctx.executeTool()`, such as
  codemode scripts and MCP-backed tools.
- `Usage` gained optional `reasoning` (subset of `output`) and `cacheWrite1h`
  (subset of `cacheWrite`).
- Content blocks gained provider-specific opaque fields: `textSignature`,
  `thinkingSignature`/`redacted`, `thoughtSignature`, and `namespace`.
- Coding-agent roles (`bashExecution`, `custom`, `branchSummary`,
  `compactionSummary`) are persisted in message entries and complete the
  `AgentMessage` union.
- `message-types.md` documents `SystemMessage.replace?: boolean` (a complete new
  baseline). It is **not** declared by the 0.99.1 `pi-ai` types and was not
  observed in local sessions; verify before relying on it.
- Compaction keeps `firstKeptEntryId` required and documents the retain-none
  case: the compaction stores its own ID when no preceding entries are kept.

## Ground rules

- Never modify session files. Treat JSONL sessions as append-only history.
- The first line is the session header, not a tree entry.
- Session entries form a tree via `id` / `parentId`; whole-file jq includes abandoned branches.
- For active-branch analysis, trace backward from the current leaf through `parentId`.
- `.message.content` is not uniform:
  - user content can be a string or content-block array
  - assistant content is an array of text/thinking/toolCall blocks
  - tool results are content-block arrays
- Message roles are `user`, `assistant`, `toolResult`, `system`, and the
  coding-agent roles `bashExecution`, `custom`, `branchSummary`, and
  `compactionSummary`; augmented hosts can add custom roles, so tolerate unknowns.
- `custom` entries are extension state and do **not** enter LLM context.
- `custom_message` entries are extension-injected context and **do** enter LLM context.
- `usage` entries, `label` and `session_info` entries, and tool-result `nestedCalls`
  are accounting/state only and do not enter LLM context.
- `context_edit` entries change only future model context; raw history, UI, and
  accounting keep the original contribution (latest edit on the active branch wins).
- Subagent `.jsonl` files use the normal Pi session format; the subagent-specific bit is the manifest path and metadata.

## Schema cheat-sheet

The header is `{type: "session", version: 3, id, timestamp, cwd, parentSession?}`.
Other entries have `{type, id, parentId, timestamp}`; entry timestamps are ISO
strings, while nested message timestamps are Unix milliseconds.

| Entry type              | Payload fields and meaning                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `message`               | `message.role`, `message.content`, `message.timestamp`                                                             |
| `model_change`          | `provider`, `modelId`                                                                                              |
| `thinking_level_change` | `thinkingLevel`                                                                                                    |
| `usage`                 | `kind`, `provider`, `model`, `usage`, optional `note`; accounting outside assistant messages                       |
| `compaction`            | `summary`, `firstKeptEntryId` (required), `tokensBefore`, optional `details`, `usage`, `fromHook`, `systemMessage` |
| `branch_summary`        | `fromId`, `summary`, optional `details`, `usage`, `fromHook`                                                       |
| `context_edit`          | `targetId`, `replacement: null` or `{content}`; latest edit on the active branch wins                              |
| `custom`                | `customType`, optional `data`; extension state                                                                     |
| `custom_message`        | `customType`, `content`, `display`, optional `details`; injected context                                           |
| `label`                 | `targetId`, `label` (undefined clears)                                                                             |
| `session_info`          | optional `name`                                                                                                    |

Message content and metadata:

- User content is a string or `(TextContent | ImageContent)[]`.
- Assistant blocks:
  - `{type: "text", text, textSignature?}`; `textSignature` is opaque provider metadata
  - `{type: "thinking", thinking, thinkingSignature?, redacted?}`; a redacted block keeps
    its encrypted payload in `thinkingSignature`
  - `{type: "toolCall", id, name, arguments, thoughtSignature?, namespace?}`; `namespace`
    is an OpenAI Responses namespace for dynamically loaded or namespaced tools
- Assistant metadata: `provider`, `model`, `api`, `stopReason`, `usage`, and optional
  `thinkingLevel` (persisted per response), `rawStopReason` (provider-native, observed
  commonly), `responseModel`, `responseId`, `providerThinkingLevel`, `diagnostics`,
  `errorMessage`, `endTurn`, and `deferred`. `"pending"` is stream-only and is not persisted.
- Tool results carry `toolCallId`, `toolName`, `content[]`, `isError`, and optional
  `details`, `usage` (nested model work, counted in session totals), and `nestedCalls`.
  `nestedCalls` is `{calls: NestedToolCallRecord[], complete}`; each record has `id`,
  `name`, `status` (`ok`/`error`/`unfinished`), optional `arguments`/`argumentsBytes`,
  `durationMs`, and `error`.
- `usage` fields: `input`, `output`, `cacheRead`, `cacheWrite`, optional `cacheWrite1h`
  (subset of `cacheWrite`) and `reasoning` (subset of `output`, do not double count),
  `totalTokens`, and `cost.{input,output,cacheRead,cacheWrite,total}`.
- System messages carry `sections` patches (`null` removes a section) and
  `toolsAdded` / `toolsRemoved`; replay them to recover the prompt/tool state.
  `message-types.md` also documents `replace: true` as a complete new baseline, but
  0.99.1 types do not declare it and local sessions do not use it.
- Compactions can checkpoint the prompt/tool state in `systemMessage`; that checkpoint
  becomes the leading system message of the compacted context. A retain-none compaction
  stores its own ID in `firstKeptEntryId`.

## Conversation text

```bash
# All user messages, handling string and content-block array forms
jq -r 'select(.type == "message" and .message.role == "user") |
  .message.content |
  if type == "string" then .
  else [.[] | select(.type == "text") | .text] | join("\n")
  end' "$SESSION"

# All assistant text responses, excluding thinking and tool calls
jq -r 'select(.type == "message" and .message.role == "assistant") |
  [.message.content[] | select(.type == "text") | .text] |
  join("\n") | select(length > 0)' "$SESSION"

# Chronological message-role sequence
jq -r 'select(.type == "message") | .message.role' "$SESSION"
```

## Tool and file usage

```bash
# Tool call counts
jq -r 'select(.type == "message" and .message.role == "assistant") |
  .message.content[] | select(.type == "toolCall") | .name' "$SESSION" |
  sort | uniq -c | sort -rn

# Failed tool results with preview
jq -c 'select(.type == "message" and .message.role == "toolResult" and .message.isError == true) |
  {tool: .message.toolName,
   preview: ([.message.content[] | select(.type == "text") | .text[:240]] | join(" "))}' "$SESSION"

# All files touched by read/edit/write tool calls
jq -r 'select(.type == "message" and .message.role == "assistant") |
  .message.content[] |
  select(.type == "toolCall" and (.name == "read" or .name == "edit" or .name == "write")) |
  .arguments.path' "$SESSION" | sort -u

# Repo edit tool: replacement count (inspect arguments for other edit tools)
jq 'select(.type == "message" and .message.role == "assistant") |
  .message.content[] | select(.type == "toolCall" and .name == "edit") |
  {path: .arguments.path, replacements: (.arguments.edits | length)}' "$SESSION"

# Bounded nested tool calls recorded on a tool result (ctx.executeTool/codemode)
jq -c 'select(.type == "message" and .message.role == "toolResult" and .message.nestedCalls != null) |
  {tool: .message.toolName, complete: .message.nestedCalls.complete,
   calls: [.message.nestedCalls.calls[] | {name, status, durationMs}]}' "$SESSION"
```

## Costs and dashboard

```bash
# Assistant-message cost subtotal and row count (not all session spending)
jq -s '[.[] | select(.type == "message" and .message.role == "assistant") |
  .message.usage.cost.total] |
  {total_cost_usd: add, assistant_turns: length}' "$SESSION"

# Compact whole-file dashboard. Reminder: includes abandoned branches.
jq -s '
  (.[0] | {session_id: .id, cwd: .cwd, started: .timestamp, parentSession}) +
  {
    entries: ([.[] | select(.type != "session")] | length),
    messages: [.[] | select(.type == "message")] | length,
    user_msgs: [.[] | select(.type == "message" and .message.role == "user")] | length,
    assistant_turns: [.[] | select(.type == "message" and .message.role == "assistant")] | length,
    tool_calls: [.[] | select(.type == "message" and .message.role == "assistant") |
      .message.content[] | select(.type == "toolCall")] | length,
    tools: ([.[] | select(.type == "message" and .message.role == "assistant") |
      .message.content[] | select(.type == "toolCall") | .name] |
      group_by(.) | map({(.[0]): length}) | add),
    errors: [.[] | select(.type == "message" and .message.role == "toolResult" and .message.isError == true)] | length,
    nested_tool_calls: ([.[] | select(.type == "message" and .message.role == "toolResult" and .message.nestedCalls != null) |
      .message.nestedCalls.calls[]] | length),
    total_cost: ([.[] |
      if .type == "message" and (.message.role == "assistant" or .message.role == "toolResult")
        then .message.usage.cost.total
      elif .type == "usage" or .type == "compaction" or .type == "branch_summary" then .usage.cost.total
      else empty end] | map(select(. != null)) | add // 0),
    compactions: [.[] | select(.type == "compaction")] | length,
    branch_summaries: [.[] | select(.type == "branch_summary")] | length
  }
' "$SESSION"
```

Tool-result `usage` covers nested model work (codemode `models.classify()`,
`ctx.executeTool()` results) and is included above so dashboard totals match
session accounting; assistant-message cost alone undercounts those sessions.

## Active branch extraction

Most jq snippets above inspect the whole file. For branched sessions, use the
active branch to isolate the selected history. This is not the reconstructed model
context: compaction and `context_edit` change what the model sees. For exact
context use the installed `buildSessionProjection` / `buildContextEntries` /
`buildSessionContext` APIs with the known leaf, or follow their implementation
read-only. Do not load old sessions through a mutating resume/migration path just
to inspect them.

```bash
# Print active-branch entries as compact JSON, newest leaf inferred from final entry.
# This assumes the final non-header entry is the current leaf, which matches normal
# append-only session use.
jq -s '
  . as $all |
  ($all | map(select(.type != "session"))) as $entries |
  ($entries | map({key: .id, value: .}) | from_entries) as $byId |
  def walk($id):
    if $id == null then []
    else ($byId[$id] as $e | walk($e.parentId) + [$e])
    end;
  walk(($entries[-1] // {}).id)
' "$SESSION"
```

Pipe that into additional jq filters when whole-file analysis would be misleading.
Use a known active leaf instead of the final entry when available; branch
navigation without a subsequent append is not recoverable from this heuristic.

## Subagent sessions

This repo's subagent extension stores each subagent run as a normal Pi session
file plus a parent-scoped manifest:

```text
~/.pi/agent/subagent-sessions/--<cwd-encoding>--/<parent-session-id>/
  manifest.json
  <uuid>.jsonl
```

The repo-owned `manifest.json` envelope is `{parent: {sessionFile, sessionId},
cwd, subagents: [...]}`. `swarm-manifest.json` instead has `swarms[]` entries
with `id`, `target`, `description`, `prompt`, `timestamp`, and `members[]`; each
member has `name`, optional `sessionId` / `sessionFile`, and `lastExitCode`.
These schemas follow the extension revision, not the Pi release.

Single-agent manifest entries include:

- `id`
- `agent`
- `agentSource`
- `description`
- `prompt`
- `sessionFile`
- `timestamp`
- `exitCode`
- `usage.{input,output,cost}`
- `durationMs`
- `provider`
- `model`
- `thinking`
- `attempts[]`

```bash
# Locate subagent runs for a parent session
PARENT_ID=$(head -1 "$SESSION" | jq -r '.id')
PARENT_CWD=$(head -1 "$SESSION" | jq -r '.cwd')
SUBAGENT_DIR=~/.pi/agent/subagent-sessions/--$(echo "$PARENT_CWD" | sed 's|^/||;s|/|-|g')--/$PARENT_ID

# List subagent runs
jq -r '.subagents[] |
  "\(.agent) [\(.agentSource)] \(.description) — exit:\(.exitCode) \(.durationMs)ms $\(.usage.cost)"' \
  "$SUBAGENT_DIR/manifest.json" 2>/dev/null

# Cost/duration summary
jq '{total_cost: [.subagents[].usage.cost] | add,
     total_duration_ms: [.subagents[].durationMs] | add,
     count: (.subagents | length),
     by_agent: [.subagents | group_by(.agent)[] |
       {agent: .[0].agent, count: length, cost: [.[].usage.cost] | add}]}' \
  "$SUBAGENT_DIR/manifest.json" 2>/dev/null

# Failed subagents
jq '.subagents[] | select(.exitCode != 0) |
  {agent, description, exitCode, prompt: .prompt[:240]}' \
  "$SUBAGENT_DIR/manifest.json" 2>/dev/null

# Tool usage per subagent session
for f in "$SUBAGENT_DIR"/*.jsonl; do
  echo "=== $(basename "$f") ==="
  jq -r 'select(.type == "message" and .message.role == "assistant") |
    .message.content[] | select(.type == "toolCall") | .name' "$f" |
    sort | uniq -c | sort -rn
done
```
